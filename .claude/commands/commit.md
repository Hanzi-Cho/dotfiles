# /commit — 원자적 커밋 메시지 추천

사용자 인자: `$ARGUMENTS`

---

## 0단계. 대상 저장소 결정 (먼저 수행)

아래 순서로 대상 저장소 `<REPO>`를 정한다. **정해지기 전에는 diff를 읽지 않는다.**

1. `$ARGUMENTS`가 있으면 그것을 경로 또는 저장소 이름으로 보고 해석한다.
   이름만 주어졌으면 현재 디렉터리 하위에서 매칭되는 저장소를 찾는다.
2. 인자가 없으면 현재 디렉터리에서 `git rev-parse --show-toplevel`을 실행한다.
   성공하면 그 경로가 `<REPO>`다. → 3단계로 간다.
3. 실패하면(= 홈 경로·워크스페이스 루트 등 저장소 밖) **즉시 `AskUserQuestion`으로 물어본다.**
   - 후보 수집: `find . -maxdepth 3 -name .git -type d` 로 저장소를 찾고,
     각각 `git -C <경로> status --porcelain` 으로 **변경사항이 있는 것만** 남긴다.
   - 후보가 2개 이상이면 질문한다. 각 선택지의 `description`에는
     그 저장소에서 바뀐 대표 파일·영역을 한 줄로 요약해 넣어 사용자가 바로 고를 수 있게 한다.
   - 후보가 정확히 1개면 묻지 않고 그것을 쓴다.
   - 후보가 0개면 `변경사항 없음` 한 줄만 출력하고 종료한다.
   - **질문에 답을 받기 전에 절대 다음 단계로 넘어가지 않는다.**

이후 모든 git 명령은 `git -C <REPO> ...` 형태로 실행한다.

## 1단계. 변경사항 수집

`<REPO>` 기준으로 아래를 읽는다. **읽기 전용 명령만 쓴다.**

- `git -C <REPO> status --porcelain=v1` — 스테이징/미스테이징/untracked 전체 목록
- `git -C <REPO> diff` — 스테이징 안 된 변경
- `git -C <REPO> diff --staged` — 스테이징된 변경
- `git -C <REPO> log --oneline -10` — 기존 커밋 스타일(scope 명명, 한글 여부, 본문 형식) 참고
- untracked 신규 파일은 diff에 안 잡히므로 `git -C <REPO> status`에서 뽑아 파일 리스트에 포함한다.
  내용이 궁금하면 `head`로 앞부분만 확인한다.

diff가 크면 `--stat`으로 먼저 전체 지형을 잡고, 관심사 분리에 필요한 파일만 본문을 읽는다.

## 2단계. 원자적 단위로 분리

- 한 커밋은 **하나의 관심사(concern)만** 담는다. "기능 A 수정"과 "문서 정리"는 다른 커밋이다.
- 파일이 아니라 **변경의 의도**로 나눈다. 한 파일이 두 관심사에 걸치면
  해당 커밋의 파일 리스트에 양쪽 다 적고, 파일명 뒤에 `(일부 hunk)`를 붙인다.
- 신규 모듈과 그것을 쓰는 수정이 함께 있으면, 중간 커밋이 깨지지 않는 순서로 배열한다.
- 커밋 순서는 논리적 순서(기반 → 사용, 기능 → 문서)를 따른다.

## 3단계. 출력

### 출력 규칙 (엄격히 준수)

- **커밋 메시지 외의 텍스트를 절대 출력하지 마라.** "분석하겠습니다", "추천해드릴게요",
  요약 설명, 마무리 멘트, 다음 단계 안내 전부 금지.
  - 유일한 예외 2가지: 0단계의 저장소 선택 질문, 후보가 없을 때의 `변경사항 없음` 한 줄.
- 각 커밋 블록은 아래 포맷을 **정확히** 따른다.

```
<커밋할 파일 리스트>

type(scope): 한글로 1줄 요약

- 세부 수정 사항 1
- 세부 수정 사항 2
```

- `type`은 `feat`, `fix`, `docs`, `chore`, `refactor` 중 하나.
- 1줄 요약과 세부 사항은 한글로 작성한다. 단, **커밋 타입 / 수정한 모듈·feature 이름 /
  파일명 / 기술명(라이브러리·API·함수명 등)은 원문 그대로** 둔다.
- 세부 수정 사항은 **최대 6개**로 제한한다.
- 설명은 초·중급 개발자가 바로 이해할 수 있는 수준으로 쉽게 쓴다.
  과한 전문 용어나 내부 구현 디테일 나열은 피하고, **"무엇을 왜 바꿨는지"**가 드러나게 한다.
- 커밋 블록 사이는 `------------------------` 구분선으로 나눈다.
- 맨 마지막에, 이 diff 전체를 **하나의 커밋으로 합칠 경우**의 메시지를
  `======= 전체 1커밋 =======` 구분선 아래 하나 더 추가한다.

### 출력 예시 (형식만 참고)

```
src/monitoring/spec.ts
docs/REQ-012.md

fix(monitoring): 요구사항 명세 불일치 수정

- 명세와 실제 동작이 어긋나던 부분을 명세 기준으로 맞춤
- 관련 문서의 조건 설명을 실제 로직과 일치하도록 갱신

------------------------

src/components/CountView.tsx

refactor(count-view): 카드 렌더링 로직 정리

- 중복되던 카운트 계산을 한 곳으로 모음
- 조건 분기를 단순화해 읽기 쉽게 정리

======= 전체 1커밋 =======

fix(monitoring): 모니터링 명세 정합성 및 카드 렌더링 정리

- 요구사항 명세와 실제 동작 불일치 수정
- CountView 카드 렌더링 로직 정리
```

## 금지 사항

- **실제로 스테이징하거나 커밋하지 마라. 제안만 출력한다.**
- `git add` / `git commit` / `git reset` / `git checkout` / `git stash` / `git push` 등
  저장소 상태를 바꾸는 명령을 실행하지 마라. 이 명령은 **읽기 전용**이다.
- 파일을 편집하지 마라.
